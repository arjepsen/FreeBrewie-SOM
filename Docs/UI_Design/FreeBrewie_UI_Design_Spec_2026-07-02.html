FreeBrewie UI Design Spec

Date: 2026-07-02. This is the working design document for the first product-shaped FreeBrewie SOM UI. It combines navigation, visual direction, screen roles, and 272x480 mockups in one place so the implementation can follow a concrete target.

The mockups are intentionally close to what we should build in LVGL first: dark charcoal backgrounds, original Brewie-like orange accents, compact labels, large touch targets, stable live data regions, and no expensive full-screen animation.

Current Hardware Constraints

Display

Logical: 272x480 portrait

Physical: 480x272 landscape scanout

Backend: custom rotated DRM

Touch

Device: Goodix touchscreen

Path: /dev/input/event0

Status: LVGL click events proven

Performance

Good: partial redraws and local movement

Avoid: continuous full-screen redraws

Goal: calm, responsive appliance UI

Safety

Now: diagnostics and placeholders

Later: actions gated by logic and MCU interlocks

Near-Term Navigation

The first implementation should be small: Home starts the product-shaped app, Status keeps the proven diagnostics, and the other sections are safe placeholders until their logic exists.

Startup
Later splash. For now, app can enter Home after init.
Home
Machine summary, MCU link, safe next actions.
Status
Diagnostics screen. First working navigation target.
Manual
Placeholder until service actions are safe.
Clean
Placeholder until clean workflows are modeled.
Settings
Placeholder. Display/touch facts first later.
Fault
Can interrupt any normal screen once fault UI exists.

Screen Roles

Home

Normal landing screen. It should answer: ready, connected, and what can I do next?

Status

Developer/service diagnostics. Keep it available, but do not let it define the product UI.

Manual

Later direct service actions. No actuator control until logic and MCU boundaries are clear.

Clean

Later cleaning workflows. Inspired by old short/full/drain/unclog options.

Settings

Later display, touch, network, system, and service settings.

Fault

High-priority blocking state. Unsafe actions should not remain available.

Implementation Checklist

  1. Add Screen_home.c and Screen_home.h.
  2. Add small app navigation state instead of direct hardware actions in button callbacks.
  3. Start on Home after app/platform/comms/UI initialization.
  4. Make Home's Status button open the existing diagnostics screen.
  5. Add safe placeholder screens for Manual, Clean, and Settings.
  6. Remove the temporary Touch OK proof button once normal navigation proves touch.
  7. Add fault banner or fault screen after home/status navigation is stable.
