# FreeBrewie SOM

_Last updated: 2026-08-03_

## Purpose
This repository contains the current SOM-side application work for FreeBrewie.

The SOM side owns:
- UI
- business logic
- higher-level machine intent
- recipe and manual-service workflows
- communication with the MCU

The MCU side owns:
- hardware execution
- measurements
- interlocks
- fault handling
- startup gating
- shutdown behavior

The shared system control model is defined in the protocol and MCU documents.

The current known-good target state is:

- `brewie.service` starts `/opt/brewie/brewie_app`
- `/dev/ttyS1` opens successfully

- a manual admin flashing helper now exists at `Deploy/Admin/flash_mcu_from_som.sh`
- heartbeat is sent from the SOM
- `STATUS_REPORT` frames are received from the MCU
- `FAULT_REPORT` frames can also be received
- target DRM display init works
- live status/debug text has been shown on the SOM display
- serial/comms still work while display is active
- touch input is mapped into LVGL in portrait coordinates
- a temporary status-screen button proves LVGL click events
- a first Home/menu/navigation shell works in the simulator
- the first Home/menu/status shell has also been verified on the real SOM display
- real SOM touch works in that shell
- MCU RX sequence numbers keep increasing while the UI is running
- CPU use was first observed around 1.4-1.7%, then around 0.7% after the first

  validating, or affecting hardware

So the project is no longer only in a headless serial state.
The first target-side display and touch bring-up milestones have now been reached.

## Current UI/display status
The current display milestone is intentionally small:

- Linux DRM is now used on the SOM target display path
- the first visible screen proof is a simple portrait live status/debug text render
- this is still a bring-up/debug stage, not a finished UI
- touch input is integrated through LVGL evdev
- the Goodix touchscreen is used through `/dev/input/event0`
- Home is now the user-facing starting point, with Status reachable through the menu

The current UI is still early. Home/menu/status are functional scaffolding, not final
product polish.

Important UI notes:

- the current target display proof is now portrait
- the platform display layer maps logical 272x480 LVGL output into the physical 480x272
  DRM scanout buffer
- continuous full-screen animation is visibly choppy on the A13 SOM, so final status/home
  screens should use partial redraws, short transitions, and targeted motion
- a true animated boot/splash screen is wanted later during SOM startup, separate from the
  live status screen

## Runtime user and deployment model
The current SOM setup uses:

- `admin` = login / maintenance user
- `brewie` = runtime / appliance user

Important current facts:

- `brewie` is runtime-only
- `brewie` uses `/usr/sbin/nologin`
- runtime install path is `/opt/brewie`
- managed service is `brewie.service`

Manual bring-up is done by logging in as `admin`, installing the binary to `/opt/brewie`, and running it as `brewie`.

---

## Current manual deployment flow

### Build on the Debian VM
Typical target build flow in VS Code:

1. `CMake: Delete Cache and Reconfigure`
2. `CMake: Build`

Target build directory:

- `build-target`

Target binary:

- `build-target/Apps/BrewieApp/brewie_app`

### Copy to the SOM
Example:

```bash
scp build-target/Apps/BrewieApp/brewie_app admin@<som-ip>:/home/admin/brewie_app
scp -r Data admin@<som-ip>:/home/admin/Data
```

### Install on the SOM
```bash
sudo install -o brewie -g brewie -m 0755 /home/admin/brewie_app /opt/brewie/brewie_app
sudo install -d -o brewie -g brewie -m 0755 /opt/brewie/Data
sudo install -o brewie -g brewie -m 0644 /home/admin/Data/styles.json /opt/brewie/Data/styles.json
```

### Manual run on the SOM
```bash
sudo -u brewie /opt/brewie/brewie_app
```

## Current build environment notes
The current target build uses:

- Debian VM host
- `amd64` host architecture
- ARM hard-float cross target
- `toolchain-armhf-bullseye.cmake`
- sysroot at `/opt/sysroots/bullseye-armhf`
- normal target build type: `RelWithDebInfo`
- normal target optimization flags: `-O2 -g -DNDEBUG`
- A13 CPU/FPU flags: `-mcpu=cortex-a8 -mfpu=neon -mfloat-abi=hard`
- LVGL target software drawing uses the NEON assembly/intrinsics path for supported
  RGB565 blend/convert operations

For the current DRM display path, the VM needed:

- `armhf` foreign architecture enabled
- `libdrm-dev:armhf`
- DRM headers visible to the build
- DRM libraries available inside the target sysroot

The SOM runtime also needed:

- `libdrm2`

These details matter for continuing target display work.

## Current code-structure intent

### `main.c`
Owns:
- program entry
- top-level init call into the app
- thin main loop

### `App.c`
Owns:
- top-level application orchestration
- initialization order between platform, comms, logic, and UI
- periodic update coordination

### `Logic/Process_plan`
Owns:
- the common ordered process-plan shape generated from basic recipe data today
- the future common shape for advanced and expert recipe editors

### `Logic/Process_runner`
Owns:
- the current process-plan step while a prepared plan is being walked
- carried machine targets that stay active between process-plan steps
- prompt/complete/error runner state

Current important limit:
- it does not yet advance from duration/sensor exits
- it does not yet send `CONTROL_SNAPSHOT` frames

### `Logic/Machine_targets`
Owns:
- the compact SOM-side target image that can be encoded as today's 16-byte
  `CONTROL_SNAPSHOT` payload
- SOM-only target fields that the shared protocol does not encode yet, such as cooling
  target and heater duty limit

### `Comms/`
Owns:
- transport
- frame parsing
- protocol encode/decode
- link state / heartbeat / last RX facts

### `Logic/`
Owns:
- application-side state and logic
- status-screen view model generation in `Status_view_model.c`
- higher-level state interpretation above raw transport

### `Platform/`
Owns:
- target/simulator platform glue
- display backend setup
- timing
- logging

### `UI/`
Owns:
- screen construction
- screen update functions
- UI-only presentation logic
- screen-local cached visible text, so unchanged LVGL labels are not dirtied

This separation is deliberate:
communication should not be folded into UI code.

## Current next-step direction
The current code and docs now support this next-step direction:

1. keep the proven comms baseline intact
2. keep comms separate from UI
3. continue the target display/UI bring-up from the working DRM baseline
4. keep the current `Screen_status` code focused as a scrollable live diagnostics screen
5. keep a true animated boot/splash screen separate as a future startup phase
6. keep touch/input owned by the platform layer
7. evolve the Home/menu shell without mixing hardware actions into button callbacks
8. keep Recipes, Extras, Settings, and Status as top-level navigation destinations
9. use the old UI as the screen/functionality reference while keeping the new C/LVGL code
   modular, readable, safe, and optimized
10. route real brew-start work through `Process_plan`, `Process_runner`,
    `Machine_targets`, and then controlled MCU snapshot sending

The immediate next phase is therefore logic integration around the existing UI scaffold:
preflight, selected-recipe commit/save flow, and safe target-snapshot sending. UI expansion
should continue, but not by putting hardware behavior directly in screen callbacks.
